# Security Policy

## Reporting a vulnerability

Please report security issues privately through GitHub's **Report a vulnerability** button on the Security tab of this repository. Do not open a public issue. You will get an acknowledgement within 72 hours and a fix or mitigation plan as soon as the issue is confirmed.

## Supported versions

Security fixes are released for the latest `main` branch.

## Security model

### Two-layer tenant isolation

Every sub-account (tenant) is isolated twice:

1. **Application layer.** All tenant data access goes through `withTenant()` / `withTenantSlug()` in `src/lib/tenant.ts`. It opens a transaction, verifies on the server that the signed-in user belongs to the agency and, for members, has a membership on that sub-account, then runs the query.
2. **Database layer.** Postgres row-level security (`drizzle/0001_row_level_security.sql`) is enabled **and forced** on every tenant table. Policies compare `sub_account_id` with `current_setting('app.current_sub_account')`, which is set with `set_config(..., true)` (equivalent to `SET LOCAL`) inside the same transaction, so it can never leak to another request on a pooled connection.

The application connects as `agencykit_app`, a role created by the migration script with `NOSUPERUSER NOBYPASSRLS` and DML-only grants. Migrations and seed scripts use a separate admin connection. `npm run test:isolation` proves that tenant A cannot read, insert, update or delete tenant B rows.

Public website endpoints resolve a published site or a widget API key through two narrow `SECURITY DEFINER` functions that return only the ids needed to open a tenant context.

### Authentication and sessions

- Passwords: bcrypt cost 12, minimum 12 characters.
- Sessions: HS256 JWT signed with `AUTH_SECRET` (generated by `scripts/setup.sh`, 64 random bytes) in an `httpOnly`, `Secure`, `SameSite=Lax` cookie with a 7-day expiry. The user is re-loaded from the database on every request.
- Login is rate limited per IP and email (token bucket). Unknown emails take the same time as wrong passwords.
- The first signup creates the agency owner; signup then closes unless `ALLOW_SIGNUP=true`.
- Server actions are protected by Next.js Origin checks. The JSON API (`/api/v1`) requires `Content-Type: application/json` and a same-origin `Origin` header.

### Input handling

- Every input is validated with zod. All queries are parameterized through Drizzle ORM or tagged templates.
- Public forms have a honeypot field, a body size limit and per-IP rate limits. Chat messages are capped at 1,000 characters.
- CSV exports neutralize spreadsheet formula injection.
- Chat widget API keys are shown once and stored as SHA-256 hashes.

### HTTP hardening

- Per-request nonce Content Security Policy with `strict-dynamic`, no `unsafe-eval` in production, `object-src 'none'`, `frame-ancestors 'none'` (public websites: `'self'`).
- HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`, `X-Frame-Options`; `X-Powered-By` is disabled.

### Deployment

- Docker Compose binds Postgres and the app to `127.0.0.1` only. There are no default passwords: `scripts/setup.sh` generates them and writes `.env` with mode 600.
- The runtime image runs as a non-root user, has npm removed and uses Next.js standalone output.
- Put a TLS-terminating reverse proxy (Caddy, Nginx, Traefik) in front for production and set `APP_URL` to the https address.

### Automated checks

`.github/workflows/security.yml` runs CodeQL, `npm audit`, gitleaks, OSV-Scanner and the tenant isolation test on every push and pull request. Dependabot keeps npm packages, Docker base images and GitHub Actions current.
